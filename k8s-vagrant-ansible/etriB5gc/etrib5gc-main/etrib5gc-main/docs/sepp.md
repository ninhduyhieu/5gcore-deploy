### Things a SEPP manages:
 ### List of SEPP peers
 - grouped by PlmnId
 - peers are similar, serving multiple services (UDM, AUSF, SMF, PCF)

### List of local NFs
 - local NFs are on the same network with the SEPP
 - each one should have an NF id generated by the SEPP. It is 1-1 mapping to the uuid[gwId] of the NF (in case of stateful) or service Id (in case of stateless). This id allows the SEPP to know how to send a request from remote network to a right target in its network

### List of remote NFs
 - remote NFs are NFs from a remote network. A remote NF is attached to a remote SEPP.
 - The SEPP should generated a localId for each remote NF. A local NF can reach to this remote NF through the SEPP with the local Id.
 - A remote NF also have a tuple of a remote SEPP and a nfId generated by that SEPP.

### Handle egress at SEPP (from a local NF to a remote SEPP):

#### Case 1 -  a request from local pod [V-network] toward a remote NF [H-network]
 - if the request has the localId for the remote NF, the local SEPP will find the remote SEPP and nfId for the remote NF on that SEPP. It then can forward the request. With given nfId, the remote SEPP know how to forward the request to its destination.

 - if it has no localId, the local SEPP will look for the 'Host' header to get the requested service Id. From this it can select a remote SEPP to forward the request. The remote SEPP should find and pick a destination from its local endpoints to forward the request. In the response, the remote SEPP should inject a header to indicate the nfId of the remote NF. The local SEPP will add to its managed list a RemoteEndpoint that have a mapping of a localId and a typle of the remote SEPP and the received nfId.

 - handle the callback information: the request may have a callback information for the remote NF to notify the requesting NF. The local SEPP should generate a nfId then rewrite the callback with a tuple of its address and the nfId. At the other end, the remote SEPP will add a new RemoteEndpoint with a mapping of the receive tuple and a generated localId. The remote SEPP will then rewrite the call back with a tuple of its own address and the local Id. 

#### Case 2 -  a callback notification from local pod [H-network] toward a remote NF [V-network]
- A callback value received by an NF consists of an address value [uuid + gwId] and an optional header value [localId].  The address allow a callback notification either reach to its final destination (in case of the target is on the same network) or a local SEPP (in case of cross network notification). In the later case, the SEPP uses the localId value from the request header to find the remote SEPP and the nfId of the remote NF, then forwarding procedure is similar to the case 1.

### Handle ingress at SEPP (from a remote SEPP to a local NF):

### case 1 - a request from a remote network through a remote SEPP
 - if the request has an nfId in its header, the local SEPP can find the target local endpoint to forward the request

 - if the request has no nfId in its header, the local SEPP should get the requested service Id from the request header ("Host" header value) then pick a local NFs serving the service to forward the request. The picked NF should now have an nfId generated. The local SEPP then attach this nfId in the corresping respone to tell the remote SEPP that any subsequence requests for the same target should have nfId included in their headers.

 - handling callback information:  the received callback should have the remote SEPP url and and nfId. The local SEPP should create and add to its managed list a RemoteEndpoint with the mapping of a newly generated localId and the tuple of the remote SEPP url and the nfId. The local SEPP then rewrite the callback with its own address and the localId.

### case 2 - a callback notification from a remote network through a remote SEPP
 - The notification from the remote SEPP should have a target header which is an nfId of a local endpoint. The local SEPP uses this information to find the address of the final destination to send the notification
